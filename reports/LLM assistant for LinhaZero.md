# Let Claude translate, let the engine decide

LinhaZero should add the LLM as a **translator and narrator around the fire engine, never as the planner**. Claude turns a coordinator's intent ("proteger Aldeias, duas equipas em 40 min, manter a N206 aberta") into a validated spec. It picks among named, pre-computed options. It explains the engine's A-vs-B results in short European Portuguese. The engine, the paired wind ensemble and deterministic code produce every cell, minute and number. The case for this split is strong. Frontier LLMs degrade sharply on grids far smaller than LinhaZero's 157 × 152 cells. In the one wildfire-specific LLM benchmark, LLM teams **did worse than doing nothing** at suppressing fire. Every success in the literature (COA-GPT, SimTIO, FunSearch, OptiMUS) pairs an LLM generator with an exact external verifier, and LinhaZero already has a fast, deterministic one. For the proof of concept, run the Claude loop in the existing .NET 10 API with the official `Anthropic` C# SDK. Stream to the browser over the same SSE pattern `RunsController` uses, and default to Claude Sonnet 5.5. A coordinator session should cost roughly **$0.60 with prompt caching** (an estimate, not a measurement). Build it in this order: explain the comparison first (read-only, lowest risk, highest demo value), then critique and briefing, then "propose a decision B" behind the engine verifier.

## LLMs fail at exactly the spatial work a containment line requires

LLM spatial reasoning collapses well before LinhaZero's grid sizes. On grid mazes, Claude-Haiku-4.5 with chain-of-thought fell from **0.78 accuracy on 5×5 to 0.24 on 9×9**. All models stayed near 0.08–0.34 when the maze was shown as a visual grid rather than an adjacency list. The named failure modes are the ones a containment line cannot tolerate: taking the straight route through walls, and treating sequential spatial questions as independent ([arXiv 2604.10690](https://arxiv.org/html/2604.10690)). On real maps, **no model of 30 tested exceeded 67%** on MapEval, and all trailed humans by more than 20 points. Distances, directions and routing were the weakest areas ([MapEval, ICML 2025](https://proceedings.mlr.press/v267/dihan25a.html)). TopoBench puts the bottleneck in *extracting* constraints from spatial representations, not in reasoning once they are extracted ([arXiv 2603.12133](https://arxiv.org/html/2603.12133)). That points straight at the fix: hand the model pre-digested, named facts.

The domain warning is sharper still. CREW-Wildfire runs GPT-4o agent frameworks on a cellular-automaton fire with slope, wind and fuel. On the "suppress fire" task the best framework scored **−593 versus −520 for "Do Nothing"**, and scouting and rescue tasks scored 0.00 for every framework. Agents cut the same trees repeatedly and kept stale plans after the fire breached a boundary ([CREW-Wildfire, TMLR 2025](https://arxiv.org/html/2507.05178v2)). FactoryFlow found hallucinations rose when compact natural-language descriptions expanded into large structured representations ([arXiv 2603.25898](https://arxiv.org/pdf/2603.25898v2)). That is exactly what happens when a model writes out dozens of `{row, col}` cells.

Nobody has published an LLM method for firebreak or containment-line placement. Published ML work is deep RL on small Cell2Fire grids, converging on grids "as large as 40 × 40 cells" ([arXiv 2404.08523](https://arxiv.org/abs/2404.08523)), plus MIP formulations that time line construction against fire arrival ([Wei et al., USFS](https://research.fs.usda.gov/download/treesearch/48943.pdf); [Belval, Wei, Bevers](https://research.fs.usda.gov/treesearch/55936)). The only well-documented wildfire LLM system, WildfireGPT, is a RAG assistant for long-term risk planning, not live tactics ([arXiv 2504.17200](https://arxiv.org/html/2504.17200v1)). LinhaZero would be novel, which helps a hackathon pitch. The flip side is that every effectiveness claim has to rest on LinhaZero's own ensemble verification, because there is no precedent to cite. One caveat runs the other way: none of these benchmarks tests a 2026 frontier model at LinhaZero scale, so newer Claude models may do better. The design should not depend on that.

## Every working hybrid pairs a generator with an exact verifier

The pattern that works is "LLM proposes, external model decides". FunSearch had an LLM write *programs* scored by an automatic evaluator and found results beyond standard baselines ([Nature 2023](https://www.nature.com/articles/s41586-023-06924-6)). The ICML 2024 LLM-Modulo position argues that LLMs cannot plan or self-verify. They should act as approximate knowledge sources inside a generate-test-critique loop with model-based verifiers ([PMLR v235](https://proceedings.mlr.press/v235/kambhampati24a.html)). COA-GPT is the closest analogue to "decision A or B". It drafts several courses of action from doctrine and mission text, a simulator scores them, and commanders refine in natural language. It reached near-expert performance after two feedback rounds ([arXiv 2402.01786](https://arxiv.org/abs/2402.01786v2)).

The gains are real but modest, and that should temper the pitch. SimTIO is the nearest simulator-in-the-loop intervention study: LLM specialists choose one-parameter refinements from validated catalogs over pre-identified bottlenecks. It found an improving plan in **86.7% of cases, versus 80.0% for a deterministic heuristic and 73.3% for grounded random search**, and the differences were **not statistically significant** ([arXiv 2609.05740](https://arxiv.org/abs/2609.05740)). OPRO-style direct optimisation matched heuristics on 10-city TSP but lost to farthest-insertion at 50 cities ([arXiv 2309.03409](https://arxiv.org/html/2309.03409v3)). The honest conclusion is that a classical generator should outdo an LLM at *where exactly the line goes*. LinhaZero's roadmap already plans one: candidate lines perpendicular to the critical path (M10 in `docs/plano/melhorias-do-motor.md`), later a min-cut on the arrival-time graph.

The LLM's best use is the step before and after the geometry. Translating natural language into formal optimisation specs is the best-studied LLM role in operations research. OptiMUS reaches about **83% on NL4Opt but only 20–45% on harder industrial sets** ([Opt-Verifier, arXiv 2605.29556](https://arxiv.org/pdf/2605.29556)). That is good enough to draft a spec a coordinator confirms, not to run unattended. Emergency-domain systems reach the same split: TopoLLM sends optimisation to tools because LLMs "neglect implicit constraints" ([TopoLLM](https://www.sciencedirect.com/science/article/pii/S2352864825001476)). WildfireGPT's best design choices transfer directly to LinhaZero. Data comes from tools, not model memory. The user confirms the profile and location before analysis. The analysis plan is user-editable. With these, it beat Perplexity on location specificity **9/9 versus 4/9** ([arXiv 2504.17200](https://arxiv.org/html/2504.17200v1)).

The research notes disagreed on one point, and the evidence settles it. One design has Claude emit polylines in grid coordinates for the server to rasterize. The other has Claude choose among **discrete, ID'd options**: anchor features, target village, resource budget and objective weights, which deterministic code turns into cells. The maze and MapEval results, the FactoryFlow expansion finding, and SimTIO's success with "validated mutation catalogs" all favour the second. Claude should output `{"anchor": "road:N206#3", "protect": "village:aldeias", "startMin": 40}`, never a coordinate list.

## Feed Claude a perception script, not a raster

Context should be compact, named, unit-annotated text, in the style of the Geospatial Awareness Layer. That system compiles geodatabase queries into a "perception script" and calls ungrounded LLMs "text-bound and blind to geography" ([arXiv 2510.12061](https://arxiv.org/html/2510.12061v2)). Raw rasters are expensive and add little. The 100 m Guimarães grid is 23,864 cells. At the current tokenizer's roughly 2.5 characters per token ([Models overview](https://platform.claude.com/docs/en/about-claude/models/overview)), one character-per-cell layer costs about 10k tokens. Four layers (fuel, slope, arrival A, arrival B) would pass 40k tokens, and the 30 m grid has about 11× more cells.

The digest LinhaZero needs largely exists already. `engine/src/explain.ts` returns, for any cell, the critical path from ignition, arrival minute, path length, mean rate, and the speed split into fuel, wind and slope shares, plus crown, head and "slowed by an action" shares. `run-result.json` carries `burnedHaByHour`, `buildingsReached` and per-village `firstArrivalMin`, and the ensemble gives win counts. Add a per-zone gazetteer (villages from `village.u16`, OSM roads, rivers and ridges from `data-prep/`) so every fact is anchored to a name coordinators know: "Aldeias, 2,1 km a NE da ignição, chegada aos 95 min em A e 140 min em B". This also builds a cheap version of the USFS "potential control locations" idea, which predicts where fires stop from roads, ridges and barriers ([USFS PCL](https://apps.fs.usda.gov/fsgisx03/rest/services/wo_spf_fam/Potential_Control_Location/ImageServer/info/iteminfo)). Those anchor features become the menu Claude chooses from.

Screenshots are cheap but untrustworthy. A 1000×1000 px image costs about 1,296 tokens, **roughly half a cent on Opus 5.5**. Anthropic itself warns that Claude's "coordinate and localization outputs are approximate" ([Vision](https://platform.claude.com/docs/en/build-with-claude/vision)). Structured adjacency text beat visual grids **86% to 34%** on 5×5 mazes ([arXiv 2604.10690](https://arxiv.org/html/2604.10690)). Images can serve an optional "o que vês no mapa?" question late in the POC. They must never be a source of intervention cells.

## Run the loop in the .NET API and stream it like a run

The Claude call belongs in the API, not the browser. Direct browser calls need a `dangerous-direct-browser-access` header, and any key in client code can be stolen ([Simon Willison](https://simonwillison.net/2024/Aug/23/anthropic-dangerous-direct-browser-access)). Server-side, the key lives only in the `api` container. Keycloak supplies the user id, and Postgres logs usage per user. The official `Anthropic` NuGet package (v10+) targets .NET Standard 2.0. It streams through `CreateStreaming` as `IAsyncEnumerable`, retries 429/5xx twice with backoff, and throws typed errors, including `AnthropicSseException` for mid-stream failures ([C# SDK](https://platform.claude.com/docs/en/cli-sdks-libraries/sdks/csharp)). Use the SDK's own types rather than the `IChatClient` adapter. LinhaZero needs cache control, effort, strict tools and structured outputs, and it is unverified whether the adapter passes them through. A single `AnthropicClient` singleton plus a concrete `AssistantService` fits the backend style rule. The API should not forward Anthropic's raw stream. It should re-emit a small app-level event set (`text_delta`, `tool_started`, `tool_finished`, `proposal`, `done`, `error`) defined in `contracts/examples/`, like every other shared type.

Tools are where grounding and control happen. Mark the proposal tool `strict: true`, which "guarantees schema validation on tool names and inputs" ([Structured outputs](https://platform.claude.com/docs/en/build-with-claude/structured-outputs)). Strict schemas cannot express `minimum`/`maximum` or array-length limits, and a request may contain at most 20 strict tools, 24 optional parameters and 16 union-typed parameters. Range checks therefore stay in server code: minutes within the duration, anchors that exist, backfires that need `litCells`. When a check fails, the tool returns `is_error` with a pt-PT message. Forced `tool_choice` returns a 400 on Opus 5.5 and Sonnet 5.5 ([migration guide](https://platform.claude.com/docs/en/about-claude/models/migration-guide)), so tool use is steered by prompt and schema. MCP is unnecessary here, with one host and one tool provider. Writing tool handlers as plain functions keeps a thin MCP server possible later, if another agency's AI host wants LinhaZero's engine ([MCP spec](https://modelcontextprotocol.io/specification/latest)).

| Tool | Kind | Returns |
|---|---|---|
| `get_scenario` | read | Ignition with place anchor, wind and weather **with provenance**, duration, A/B interventions summarised by kind, minutes, length and nearest named feature |
| `get_results` | read | Per-decision area by hour, buildings, village arrivals, ensemble wins ("B ganha em 143/200 cenários") |
| `explain_place` | read | `explainPath` output for a named village: arrival, path segments, fuel/wind/slope shares |
| `list_anchors` | read | Candidate roads, ridges and rivers near the front, with IDs, length, distance and fire arrival time |
| `propose_decision` | strict | Spec only: target, anchor IDs, start minute, resources, objective. The server generates the geometry |
| `evaluate_proposal` | engine | Single run, then paired ensemble via NATS; returns deltas against A and B only |

ADR 0070 ("incerteza sempre no servidor") already routes ensembles to the engine-worker, so `evaluate_proposal` reuses that path. The read tools and the candidate-line generator should be pure TypeScript in `engine/`. The browser and the Node worker then compute identical digests, and the .NET loop dispatches tool calls to the engine-worker. Whether the engine-worker can take a second job type cleanly still needs checking.

Model choice and cost favour Sonnet. All four current models have 1M context. Anthropic labels Sonnet 5.5 "the best combination of speed and intelligence" at **$2/$10 per MTok**, Opus 5.5 "Moderate" latency at $4/$20, and Haiku 5.5 "Fastest" from $0.10/$0.50 ([Models overview](https://platform.claude.com/docs/en/about-claude/models/overview); [Pricing](https://platform.claude.com/docs/en/about-claude/pricing)). Cache reads cost 0.05× base ($0.10/MTok on Sonnet). Cache reads also don't count toward input-token rate limits ([Rate limits](https://platform.claude.com/docs/en/api/rate-limits)). Caching is a byte-exact prefix match in the order tools → system → messages ([Prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)), so the system prompt and tool list must be byte-stable. The scenario digest goes after the cached prefix. Keep one model per conversation, because caches are model-scoped, and make "análise aprofundada (Opus)" start a fresh thread.

The estimate below assumes about 30 requests per session, 20k average context with about 85% cache reads, and 30k output tokens. It comes from the research notes, not from measurement.

| Model | Estimated session cost (cached) | Role in LinhaZero |
|---|---|---|
| Sonnet 5.5 | ≈ $0.58 (≈ $1.50 uncached) | Default for chat and proposals |
| Opus 5.5 | ≈ $1.15 | Opt-in deep analysis, or default if evals show better plans |
| Haiku 5.5 | ≈ $0.03 | Briefing drafts, eval judge |
| Fable 5.1 | ≈ $2.75 | Not suited: "Slower" latency |

At the Start tier's $500/month cap, Sonnet allows roughly 800 sessions. Set a lower Console spend limit and per-user quotas in the API as well. Anthropic publishes no absolute latency figures, so time-to-first-token is an open question the POC must measure. Ensemble runs will likely dominate wall-clock time anyway. The UX implication: stream text and show tool activity ("a correr 200 cenários de vento…"). Proposals and briefings should also run *while the coordinator keeps working*, rather than gating the map behind a chat turn.

## Grade the assistant against the engine, not against a judge

Use programmatic checks wherever the output is constrained, and keep model-graded rubrics for open prose. LinhaZero is unusually well placed for this, because the engine is an oracle. Expert-versus-LLM-judge agreement on WildfireGPT was only **63–75%** ([arXiv 2504.17200](https://arxiv.org/html/2504.17200v1)), so the judge should cover only pt-PT quality. Four case types cover the assistant. **Explanation** cases pass when every number quoted (ha, minutes, buildings, wins) appears in the tool results and no unlisted village is mentioned; a judge checks the dominant factor, pt-PT (not pt-BR) wording, and an uncertainty statement when wins are near 50%. **Proposal** cases pass when the spec validates, the anchors exist, timing is feasible and the ensemble win rate over A meets a threshold. A proposal must also beat the M10 perpendicular-line heuristic: if the LLM-chosen anchor cannot, the LLM adds no value at that step. **Critique** cases seed A with known-bad plans (a line behind the front, an upwind backfire, a drop after arrival) and check that a structured verdict flags the flaw. **Robustness** cases cover prompt injection, out-of-scope questions and missing weather.

Cases come from `sintetica`, the two replay grids (`replay-alijo-24072019`, `replay-vieiradominho-10082016`) and the PT-FireSprd validation fires. With fixed seeds (`seed: 2035`), only the LLM side varies, so three repetitions per case give a noise floor. Nightly runs can use the Batch API at 50% off ([Pricing](https://platform.claude.com/docs/en/about-claude/pricing)). One limit belongs in the docs: these evals show proposals are sensible *inside the engine*. They say nothing about real-world effectiveness, because the engine simulates no suppression beyond what is drawn.

## Conclusion: the recommended design and a four-phase POC

The finding that should shape the project is that the valuable AI work in LinhaZero has already been done by the engine. The explain record, the ensemble win counts and the planned candidate-line generator are the "verifier" and "solver" that make LLM hybrids work elsewhere. Claude's job is to make them usable in the first minutes: understand what the coordinator wants, choose among named options, and say in two sentences of pt-PT why B wins in 143 of 200 winds and when it would not. That also turns the main risk into a feature. Wins out of N, weather provenance, and tool-cited numbers are exactly the overtrust and silent-substitution guards that WildfireGPT lacked.

**Recommended design.** The browser hosts an assistant panel and a "draft decision B" layer with an "Aceitar proposta" button; nothing is auto-applied. A new `AssistantController` in `LinhaZero.Api` runs a bounded Claude loop: at most 3 proposals and 1 ensemble per user turn, with a wall-clock cap. It uses the `Anthropic` C# SDK on Sonnet 5.5 at low/medium effort, a cached byte-stable prefix (role, pt-PT rules, intervention glossary, tools), then the scenario digest. It relays app-level SSE events defined in `contracts/examples/`. Tool handlers are pure TypeScript in `engine/`, executed by the engine-worker over NATS. A migration adds append-only conversation, tool-call and `usage` tables for audit, quotas and cost tracking. The system prompt requires every outcome claim to cite a tool result, surface the ensemble win count, and state the weather source.

| Phase | Build | Done when |
|---|---|---|
| **0. Plumbing** (~2 days) | `ANTHROPIC_API_KEY` in the `api` env, SDK singleton, `AssistantController` with SSE relay, event contract JSON, usage/quota migration, Console spend limit | A pt-PT streamed reply about a posted scenario digest appears in the UI panel; token usage logged |
| **1. Explain A vs B** (first real feature) | Digest builder in `engine/` (gazetteer, place anchors, `explainPath`, results, ensemble wins); read tools `get_scenario`, `get_results`, `explain_place`; fixed short answer format (3 points + "o que mudaria a resposta") | Explanation evals pass on synthetic and replay cases: 100% of quoted numbers traceable; cache hits visible in `cache_read_input_tokens`; TTFT measured |
| **2. Critique and briefing** | Rule checks in code (line ready after arrival, upwind backfire, late drop, line not anchored) that Claude phrases; one-click "briefing A vs B para o COS" export, drafted by Haiku or Sonnet and reviewed by the user | Seeded-flaw cases flagged; briefing contains only tool-sourced figures |
| **3. Propose decision B** | `list_anchors`; strict `propose_decision` spec; server geometry from anchors (M10 perpendicular lines to the critical path, snapped to roads/ridges); `evaluate_proposal` via engine-worker; draft B layer with accept/reject | Proposals validate 100%, beat A in the paired ensemble above the threshold, and match or beat the pure-heuristic baseline on the eval set |
| **4. Optional extensions** | Natural-language scenario setup ("vento NW 30 km/h, ignição perto de X"), Opus deep-analysis toggle, screenshot Q&A, min-cut generator when the roadmap delivers it, thin MCP server | Driven by demo feedback |

Build Phase 1 first. It needs no new geometry, its claims can be checked automatically against the engine, and it already delivers the hackathon story: a coordinator asks "porque é que B protege Aldeias?" and gets a grounded answer in seconds. Phase 3 is the most impressive feature but the least proven. Ship it only if it beats the plain heuristic, and treat a failure to beat it as a valid result rather than a reason to let the LLM draw lines.
